# ADR-003: Observe scratch worktrees concurrently [status: accepted]

- **Context:** `bu prune --dry-run` took about 15 seconds on a repository with 13 scratch worktrees. `bu` observed each worktree one after another. Each observation runs about eight subprocesses: Git checks for the root folder, branch, status, and in-progress operations, plus one `gh pr list` call. The `gh` call is a network request that takes 0.5 to 1 second. The time was spent waiting, not computing.
- **Decision:** `bu prune` now observes and classifies scratch worktrees on scoped threads (`std::thread::scope`, threads that must finish before the function returns). It splits the scratch worktrees into at most 8 equal chunks, one thread per chunk. The threads run only Git commands. One `rev-parse` per worktree prints the root folder, the in-progress operation markers, `HEAD`, and the branch name (`--abbrev-ref=loose`, which shortens names exactly like `git symbolic-ref --short`). One `git status` follows it. One more thread starts first and looks up the pull requests of every unprotected branch that `git worktree list` reported for a worktree that passed the cheap checks, in one `gh api graphql` call. The lookup therefore overlaps the process check and the Git work. `bu` uses an answer only for a worktree that still needs it after its Git checks, so dirty, detached, busy, and in-use worktrees are never failed by a lookup error. If a worktree's observed branch was not in that lookup (it switched branches, or `--abbrev-ref` returned an ambiguous `heads/<name>`), `bu` asks again for the observed name after the threads finish. The call has one aliased `pullRequests(headRefName: <branch>, states: [OPEN, CLOSED, MERGED], first: 100, orderBy: CREATED_AT DESC)` field per branch. That is the same question `gh pr list --state all --head <branch> --limit 100` asks: any author, newest 100 first. The `{owner}` and `{repo}` placeholders resolve the repository the same way `gh pr list` does, including `gh repo set-default`. One call holds at most 50 branches, and larger sets use more calls, one after another. If a call fails, every worktree that needed it is reported as `failed` with the same error. Before this change each lookup failed on its own, but the rows looked the same. The cheap checks stay serial: locked, missing folder, and contains the current directory. The process check from ADR-002 follows them. It is still one `lsof -d cwd -Fpcn` call per run, not one per worktree. It runs on the main thread while the GraphQL lookup is in flight, and every in-use worktree is blocked before any Git observation starts. If that `lsof` call fails, `bu` waits for the lookup thread, discards its answer, and changes nothing, as ADR-002 requires. Results are put back in `git worktree list` order, so the output does not change. Removal stays serial. `remove_scratch` still lists the worktrees and repeats every check from ADR-001 immediately before each removal, including a fresh one-branch GraphQL lookup and then the fresh process check from ADR-002. `git worktree prune` still runs at most once.
- **Alternatives:** An async runtime or a thread-pool crate was rejected because the work is a few blocking subprocesses and the standard library is enough. A shared work queue balances slow `gh` calls slightly better, but chunking keeps the order with no extra bookkeeping. Parallel removal was rejected because removals change shared Git state (the worktree list and branch refs). Doing them one at a time keeps each recheck accurate and each failure easy to read. An unbounded thread count was rejected because many scratch worktrees would mean many parallel `git status` commands. One `gh pr list` per branch was the first design. It was replaced because each `gh` start costs a process, two Git calls to resolve the repository, and a network round trip, and the overlap only hid that cost. Waiting for every `git status` before asking GitHub was the second design. It was replaced because the one lookup then sat on the critical path. Asking about branches that turn out to be dirty costs only extra aliases in the same call.
- **Consequences:** A dry run now takes roughly the time of the slowest chunk instead of the sum of all observations. A dry run makes one `gh` call per 50 branches that need a lookup, instead of one per branch. It makes two Git calls per scratch worktree, instead of about ten. Up to 8 `git status` commands can run at once, each in its own worktree, so they do not compete for the same index lock. A real prune still pays the full serial recheck cost per removed worktree, which is the price of the safety boundary in ADR-001. Starting the lookup before `lsof` means a run whose process check fails, or whose worktrees are all in use, still makes that one read-only `gh` call.
