# ADR-004: Prune scratch worktrees whose HEAD is behind the merged head [status: accepted]

- **Context:** ADR-001 prunes a scratch worktree only when its one merged pull request has a head commit equal to local `HEAD`. The `review-pr` skill pushes review fixes from a different worktree, so the original worktree never pulls them. The pull request then merges at a later commit, and `bu prune` blocks the original worktree with `merged pull request #N has head X, not local HEAD Y`. On 2026-10-20 a dry run on the dotfiles repository blocked 4 worktrees this way (dotfiles pull requests #159, #171, #176, and #195). In each one, local `HEAD` was an ancestor of the merged head: 0 commits ahead and 1 to 4 behind. Every autonomous `/rogue` run that gets review fixes leaves one more. The fix commits were present locally only because the review worktrees share the repository's object store. A fix pushed from GitHub, Codex, or another clone would not be present.
- **Decision:** A scratch worktree is also prunable when every other check from ADR-001 to ADR-003 and `prune.keep` passes, and local `HEAD` is a strict ancestor of the head commit of its one merged pull request. The check runs only when the two commits differ, so an exact match costs nothing extra. `bu` runs `git merge-base --is-ancestor <local HEAD> <merged head>` in the worktree. Only exit status 0 counts as proof. Exit status 1 keeps today's blocked row. Any other result means the answer is unknown, and `bu` then runs `git rev-parse --verify --quiet <merged head>^{commit}`. If Git reports the commit missing, the row is blocked and reads `merged pull request #N has head X, not local HEAD Y; its head commit is not in the local repository`. Otherwise the row fails and the command exits nonzero. `bu` never fetches to fill a missing commit. After exit status 0, `git rev-list --count <local HEAD>..<merged head>` gives the distance for the row. The check runs during classification and again in the recheck immediately before removal, after the fresh pull-request lookup. The branch delete still pins local `HEAD`: `git update-ref -d refs/heads/<branch> <local HEAD>`, never the merged head. Each prunable row names the proof that matched. An exact match keeps `merged pull request #N; would remove worktree and branch`. The new case reads `merged pull request #N; local HEAD is 2 commits behind its head; would remove worktree and branch`, and `was 2 commits behind` after removal. `bu recycle` and the `forceable` status keep the exact-match rule from `docs/adr/force-recycle-merged-benches-001.md`, because they discard uncommitted files.
- **Still blocked:** The rule must keep blocking each of these cases. A test covers each one.
  - Local `HEAD` is ahead of the merged head: it has commits after the merged head.
  - Local `HEAD` has diverged from the merged head: each side has commits that the other lacks.
  - The pull request was rebased or force-pushed, so its local commits were rewritten. The old local commits are not ancestors of the new head. The worktree stays blocked even when the same changes merged.
  - The merged head commit is not in the local object store, for example a fix pushed from GitHub, Codex, or another clone.
  - The ancestry check fails or exits with a status other than 0 or 1. The row fails.
  - Every case that ADR-001 to ADR-003 and `prune.keep` already block: open, closed-only, missing, or ambiguous pull requests, dirty, locked, detached, protected, in use, or holding kept ignored files.
- **Alternatives:** Making `review-pr` pull its fixes into the original worktree was rejected as the only fix. It covers one skill, while fixes from GitHub suggestions, Codex, or another clone leave the same state. It also leaves the 4 existing worktrees blocked. Fetching a missing merged head (`git fetch origin <commit>`) would prune more worktrees. It was rejected because a dry run would write to the object store and depend on the network. Comparing trees or patch IDs to cover rebased pull requests was rejected because "the same changes merged" is weaker proof than "these commits are reachable from the merged head". `git rev-list --left-right --count` alone gives the same answer, but `git merge-base --is-ancestor` documents its exit statuses, so it is the proof and `rev-list` only counts. Treating every nonzero `merge-base` status as "not an ancestor" was rejected because it hides real Git failures from the daily job. Failing every row whose merged head is missing was rejected because that is a normal state after a fix pushed from GitHub, and the daily job would then fail every day.
- **Consequences:** The worktree that `review-pr` leaves behind is pruned once its pull request merges. The proof boundary moves from "GitHub holds this exact commit" to "GitHub holds a descendant of this commit". Every commit on the deleted branch stays reachable from the merged head, which GitHub keeps as `refs/pull/<N>/head`, so the merged pull request remains the record, as in ADR-001. The rule also widens pruning in every configured repository, not only dotfiles, and the daily `bu-prune` job acts on it after the next install. A merged head that is missing locally stays blocked until something fetches it. Each row that needs the ancestry check costs two or three more Git calls, and only those rows pay it.
